# 架构说明

这份文档解释插件为什么长这样，以及每一部分在宿主里扮演什么角色。想知道"怎么用"，读 [README](../README.md)；想知道"为什么这么做"，读这里。

## 一、问题定义

`stack-diagram` 本身是一个 agent skill：一份 `SKILL.md` 加几个 Python 脚本，教模型怎么画云架构图。它原本的用法是放在 skill 目录里，等模型在合适的时候**自己**去查。

这里有两个独立的失效点：

1. **目录里没有** —— skill 只在某个项目的 `.dsh/skills/` 或用户级 `~/.dsh/skills/` 里，换个工作目录就没了。
2. **有但不会用** —— 就算目录里有，模型也倾向于"用文字描述架构"，因为 skill 只是"可查询"，提示词里没有任何一句说"这种问题该画图"。

第 1 点用文件放置就能解决，第 2 点解决不了。而第 2 点恰恰是决定"这个技能到底会不会被用上"的那一点。

所以插件必须同时做两件事：**让技能全局可见**，**让模型知道什么时候该想起来它**。

## 二、两条接缝

DeepSeek Harness 的插件是一个 cordis 服务树。插件拿到的 `ctx` 上挂着一批服务对象，向这些对象写入就是"扩展宿主"的唯一手段。本插件用两条：

```
                    ┌──────────────────────────────┐
   profile 启动      │  cordis 插件树                │
        │           │                              │
        ├──────────▶│  ctx.skills  (SkillRegistry)  │◀── ① register(skill)
        │           │                              │
        ├──────────▶│  ctx.systemPrompt             │◀── ② section({name,order,text})
        │           │                              │
        ▼           └──────────────────────────────┘
   会话组装 ──▶ skill 目录（模型可见）  +  系统提示词（模型必读）
        │
        ▼
   模型判断"这是架构问题" ──▶ 调 skill 工具 ──▶ 读 SKILL.md ──▶ 跑脚本出图
```

### ① `ctx.skills.register()`

服务来自 `@deepseek-ai/dsh-skill`，`SkillRegistry extends Service`。`register()` 接受一个 `SkillDefinition`：

| 字段 | 取值 | 作用 |
|---|---|---|
| `name` | `stack-diagram`（来自 SKILL.md frontmatter） | 必须匹配 `/^[a-z0-9]+(?:-[a-z0-9]+)*$/` |
| `description` | SKILL.md frontmatter 的 description | 模型在目录里看到的那一句话 |
| `content` | SKILL.md 去掉 frontmatter 后的正文，19704 字符 | 模型调用 skill 时真正读到的内容 |
| `source` / `path` | `skill/SKILL.md` 的绝对路径 | 溯源用 |
| `provider` | `dsh-stack-diagram` | 让目录里能看出这条技能是谁注入的 |
| `resourceBase` | `{ kind: 'directory', path: <包>/skill }` | **最关键的一项**，见下 |
| `metadata` | `{ license, compatibility }` | 从 frontmatter 原样带出 |

`resourceBase` 是整条链里最容易被忽略的一项。SKILL.md 正文里到处是相对路径：

```
assets/template.html
assets/fonts
references/geometry.md
scripts/build.py
```

模型拿到技能后要执行 `python3 scripts/build.py ...`。如果没有 `resourceBase`，这个相对路径会以**会话工作目录**为基准解析，指向一个不存在的文件；有了它，宿主机在技能文本前插入一行：

```
Base directory for this skill: /Users/.../node_modules/dsh-stack-diagram/skill
```

文件才找得到。这是"技能能用"和"技能看起来能用"的分界线。

### ② `ctx.systemPrompt.section()`

服务来自 `@deepseek-ai/dsh-system-prompt`。`section()` 往系统提示词里插一段固定文本，按 `order` 排序。

宿主已有的 order 常量：

| order | 用途 |
|---|---|
| 600 | TEAM_POLICY |
| **700** | **本插件的路由段** |
| 800 | PTC_ONLY |
| 900 | FILE_REFERENCE |
| 5000 | TOOLS_SDK |
| 10200 | DEPLOYMENT_PERSONA_SUFFIX |

放在 700 是因为它属于"行为策略"层：要在团队策略之后（不覆盖团队规则），在工具说明之前（工具列表还没出现时模型就先有了倾向）。

路由段 1103 字符，内容只做**路由**，不教任何画图方法——方法是 SKILL.md 的职责，提示词预算要和宿主其它部分共享。它说三件事：

- **什么时候用**：架构/系统/栈/基础设施/部署图、服务拓扑、数据流、请求流、"什么跟什么说话"、任何用户想看成方框和箭头的东西。
- **什么时候主动用**：答案会变成"一堆服务名 + 箭头"的文字墙时，不用等用户说"画一张"。
- **什么时候**不**用**：小算法和状态机选 mermaid；连接少于三条时纯列表就够——真品牌图标加分组框的优势在这里不存在，反而增加阅读成本。

最后一句附带运行前提：脚本需要 Python 3.9+，PNG 需要 Playwright + Chromium。模型知道这些，才不会在缺依赖时装作画完了。

## 三、为什么两条都不能少

这是整个插件唯一的设计判断，值得单独说清：

| 只有 ① | 只有 ② | 两条都有 |
|---|---|---|
| 技能在目录里，模型点名才加载 | 提示词说"该画图"，但没有可调用的技能 | 提示词给动机，技能给方法 |
| 退化成"必须手动调用的工具" | 退化成一句无用的建议 | 自动触发 |

只注册技能时，实测现象是：给它一段架构描述，它写 800 字散文，完全不提画图。因为技能目录是"可查"，不是"会用"。这不是模型不听话，是提示词里确实没说这件事该做。

只写提示词时，模型会尝试调用一个不存在的技能名，然后放弃。

## 四、加载时序

cordis 的 `app.plugin()` 是同步返回的，但服务挂载完成要等一个 tick。这个特性在测试里是陷阱，在运行时由宿主的加载器处理好了（它按依赖顺序挂载，`apply` 被调用时 `inject` 声明的服务一定就绪）。

测试脚本里的正确写法：

```js
const app = new Context()
app.plugin(SkillService)
app.plugin(SystemPromptService)
await tick()                    // ← 少了这行，下面 app.plugin(plugin) 直接崩
app.plugin(plugin)
await tick()
const list = await app.skills.list()   // ← list() 是异步的，返回 Promise
```

两个坑叠在一起：服务晚一个 tick 可用，`list()` 又是异步的。写成 `app.skills.list().map(...)` 会得到 `TypeError: ... .map is not a function`，因为对 Promise 取 `.map`。

## 五、代码结构

`lib/index.js` 151 行，五块：

```
常量区
  PACKAGE_ROOT    ← import.meta.url 上溯一级
  SKILL_DIR       ← <包>/skill
  SKILL_FILE      ← <包>/skill/SKILL.md
  ROUTING_ORDER   ← 700
  ROUTING_TEXT    ← 1103 字符的路由段

frontmatter 解析
  splitFrontmatter(raw)  按首尾 --- 切成两半
  readFrontmatter(text)  手写 key: value 解析

技能装载
  loadSkill()  读文件 → 切 frontmatter → 校验 name/description → 组装 SkillDefinition

注入
  apply(ctx)   两次 try/catch，各自独立失败

导出
  apply.inject = ['skills', 'systemPrompt']
  export default apply
```

三个刻意的选择：

**不用 YAML 依赖。** frontmatter 就是四行 `key: value`，为了读四个字符串引入一个 YAML 解析器，等于让插件在 profile 重装依赖树时多一个可能崩的点。手写解析器 20 行，够用。

**两段注入各自 try/catch。** SKILL.md 坏掉时应该只损失画图能力，不该把整个插件行从树里摘掉——那样连路由段都没了，排查时看到的是一行笼统的 "entry did not activate"。分开捕获，日志里能直接看出是哪一半出的问题。

**`inject` 挂在函数对象上，不做命名导出。** 宿主加载器做 `exports.default ?? exports`，命名导出在解包那一步就被丢掉了。写成 `export const inject = [...]` 语法完全正确、打包也不报错，但运行时第一句 `ctx.skills` 就抛 `cannot get property "skills" without inject`。这是一个只在真机上暴露的坑，所以代码里留了注释。

## 六、包里没有的东西

- **没有图标文件**。品牌 logo 在运行时从 svgl / devicon / gilbarbara / 各厂商官方图标包抓取。理由有两个：商标不该随包分发；图标集会变，抓取总是拿到最新版。代价是第一次出图需要网络。
- **没有 Node 依赖**。`lib/index.js` 只用 `node:fs` / `node:path` / `node:url` 三个内置模块，装完不产生任何传递依赖。
- **没有构建步骤**。源码即产物，`main` 直接指向 `lib/index.js`。改一行立刻生效，不需要 `npm run build`。

## 七、失败模式速查

| 现象 | 原因 | 定位 |
|---|---|---|
| 启动报 `cannot get property "skills" without inject` | `inject` 写成了命名导出 | 看 `apply.inject` 是否在 default 导出函数上 |
| 技能在目录里，但永远不自动触发 | `inject` 少了 `systemPrompt`，第二段注入被 try/catch 吞成 warn | `app.systemPrompt.assemble({})` 检查 section 是否存在 |
| 模型调用了技能，但脚本路径找不到 | `resourceBase` 缺失或指错 | 看技能文本第一行的 `Base directory` |
| `Cannot read properties of undefined (reading 'list')` | 测试里服务还没挂载完就访问 | 两次 `app.plugin` 之间加 tick |
| `Executable doesn't exist at .../chromium_headless_shell-NNNN/...` | Playwright 与 Chromium build 号不匹配 | `python3 -m playwright install chromium`，错误信息里写了要哪个 build |
| `%%ICON_xxx%%` 残留 | `build.py` 没找到图标 | 先跑 `fetch_icons.py`，检查图标目录和名字拼写 |
